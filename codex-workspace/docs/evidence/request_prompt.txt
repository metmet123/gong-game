Codex Astra 전달용 — 「공무원 키우기」 통합 마스터 개발계획 수립 요청
0. 이번 작업의 목표와 작업 경계
너는 게임 디렉터, 시니어 게임 기획자, 2D UX 디자이너, 소프트웨어 아키텍트, QA 리드 역할을 동시에 맡는다. 첨부한 현재 실행 HTML과 복수의 기획 자료를 실제로 읽고 비교해, 「공무원 키우기 — 금일 중 제출」의 통합 마스터 개발계획을 작성하라.
이번 의뢰는 계획 수립 단계다. 현재 게임 파일을 무단 변경하거나 대규모 구현을 시작하지 마라. 기존 코드·자료는 읽기 전용으로 분석하고, 구현이 필요한 항목은 단계·TASK·완료 조건으로 세분화한다. 작성된 계획이 승인되면 다른 Codex 세션이 그대로 이어 받아 실질적으로 구현할 수 있어야 한다.
최종 목표는 단순한 미니게임 모음이 아니다. 작은 2D 구청 사무실에서 업무별 논리 퍼즐을 해결하고, 동료·사건·사무실 꾸미기·수집 도감·승진과 생활의 변화를 체험하는 성장 게임이다. 3D·비싼 그래픽·상시 서버는 피한다. 실사용 첫 플랫폼은 **Android 모바일 브라우저(세로 모드)**를 우선하고, PC 웹에서도 플레이 가능하도록 한다. 최종 빌드는 가능한 경우 오프라인 단일 HTML로 배포하는 방식을 유지하되, 개발 소스는 반드시 모듈화한다.
기획·설계가 최우선이다. 아이디어를 모호하게 나열하지 말고, 실제 콘텐츠 예시, 상태 전이, 데이터 필드, 구현 방안, UI 명세, 테스트까지 구체화하라. 예상할 수 있는 세부 사항은 스스로 권장 기본값을 정하고 이유를 기록한다. 사용자에게 사소한 선택을 계속 요구하지 마라.
1. 반드시 분석할 첨부자료 및 우선순위
   첨부자료는 다음과 같다. 실제 파일 내용과 기능을 확인하고 문서상의 주장과 구현 사실을 구분하라.
   공무원키우기_픽셀아트.html — 현재 실행 가능한 게임 코드 기준. 기존 UI·사무실 렌더러·5종 업무 퍼즐·포인트·성장 도구·꾸미기·업무 도감·일차 진행·세이브/백업 등을 실제 코드 관점에서 조사한다. 어떤 기능이 진짜 동작하는지 정적 코드 점검 및 가능한 실행 테스트로 확인한다.
   공무원키우기_생활보장과_확장상세계획.html — 생활보장과 배치 및 세부 구현 참고. 문서에 삽입된 14열 × 21행, 물품 46개의 원본 배치 JSON과 객체 좌표·크기·방향을 추출한다. 기존 퍼즐 이후 신규 8종의 3단계 확장, 해금, 저장 마이그레이션, 테스트 안을 분석한다. 그 안의 수치는 제안과 확정을 구분한다.
   공무원키우기_새버전_기획시안.html — 새로운 게임성·퍼즐 구성과 타과 협조 게임의 핵심 아이디어. 단순 기억·숫자 비교보다 규칙 이해, 여러 해법, 설계·추리를 강조한 대안을 적극 수용한다. 8종의 새 퍼즐과 타과 미니게임 후보를 누락 없이 추출한다. 이 문서의 ‘고정된 내 자리 시점’은 이번 사용자의 신규 결정인 ‘전체 지도 → 구역 이동/선택 → 카메라 확대’로 대체한다.
   공무원키우기_유사게임조사_구현제안.html — 유사 상용게임 조사와 UX/게임 메커닉 참고. 게임의 차별 요소만 취하고 타사 그래픽·UI·소스·문제 원문을 그대로 복제하지 않는다. 조사 문서의 주장과 외부 확인이 필요한 내용은 구분한다.
   Screenshot_20261010_205101_Samsung Browser.jpg — 현재 Android 모바일 브라우저에서 보이는 화면·글꼴·조작 공간·픽셀아트 분위기 참고. 실제 화면 캡처이며, 이 한 장을 ‘구역 확대 화면 구현 완료’의 증거로 간주하지 마라.
   대화에서 확정된 기획 — 기본은 순발력+추리 혼합, 난이도 하/중/상 언제든 선택 가능, 주력은 업무별 퍼즐, 사무실은 몰입을 위한 공간, 풍자는 업무절차·자료요청·기한에 집중하며 지나치게 교훈적인 결말은 피한다.
   사용자가 부르는 ‘붙임5’ = 타과 퍼즐 구상, ‘붙임6’ = 구역을 나눌 배치도, ‘붙임7’ = 구역 확대의 시각 참고라는 역할을 우선 이해하라. 첨부 안에서 번호와 파일명이 직접 대응된다는 증거가 없다면 번호를 임의로 매핑하지 말고 실제 확인한 파일명과 문서 내 해당 항목을 기준으로 인용하라. 구역 확대 참고 화면이 실제 첨부로 식별되지 않는다면 확인 불가로 기록하고, 요구된 기능 자체는 아래 명세로 설계하라.
   충돌 시 우선순위: 이번 메시지의 신규 사용자 결정 > 배치 JSON 같은 명시적 확정 원본 > 새 버전의 퍼즐 방향 > 작동하는 기존 게임·저장 호환성 > 과거 개발 제안/연구 보고서. 각 차이에 대해 기존안 / 이번 결정 / 변경 이유 / 이전 데이터 보존 방안을 작성하라. 계획서에 없는 기능을 ‘이미 구현’이라 단정하지 마라.
   별도 조사: 현재 시장의 참고 게임과 설계 패턴
   첨부된 유사게임 조사를 요약하는 데 그치지 말고, 실제로 적용할 만한 게임 디자인 패턴을 보강하라. 인터넷 검색이 가능하면 공식 게임 사이트·공식 스토어 소개·제작자 자료를 우선 확인하고 Papers, Please, Lil’ Guardsman, Human Resource Machine, Death and Taxes, Baba Is You, 캐주얼 픽셀 사무실/성장/꾸미기·도감 게임 등을 특정 설계 문제별로 비교하라. 특히 구역 탭→자동 이동→카메라 확대, 공간을 꾸미고 변화가 남는 보상, 짧은 서사 에피소드, 여러 해법을 허용하는 논리 퍼즐, 부서팩 확장을 조사한다. 앱의 이미지·문구·문제·UI를 복제하지 말고, 우리 게임에 적용할 수 있는 일반 원리 + 불필요한 요소 + 제작비 대비 효과만 추출한다. 공식 확인 사실, 사용자 첨부의 주장, 새로운 설계 제안을 구분하고 근거 URL과 확인 날짜를 적는다. 인터넷을 사용할 수 없으면 외부 확인이 끝난 것처럼 쓰지 말고, 첨부에서 확인 가능한 수준으로 작성하라.
2. 필수 게임 방향
   가칭: 공무원 키우기 — 금일 중 제출.
   핵심 비율은 **업무 퍼즐 70% / 성장·수집 20% / 사무실 연출 10%**라는 지향점으로 유지하되, 플레이 시간·기능 수의 강제 비율로 오해하지 않는다.
   하루는 기본 본업 4건 내외, 전체 6~10분, 일반 퍼즐 20~120초, 고급 설계형 퍼즐은 별도 모드에서 다소 길어질 수 있도록 제안한다. 시간이 너무 오래 걸리면 하루 필수 배치를 조정한다.
   캐릭터·사무실은 크림색/짙은 녹색/목재 계열의 단순 2D 픽셀아트를 1차 기본값으로 한다. 폰트는 선명한 실문자로 렌더링하고, 캐릭터와 소품은 자산 제작량이 적은 방식으로 설계한다.
   모든 퍼즐은 하/중/상 설정을 적용한다. 어려움은 우선 조건의 복잡성과 최적화 목표로 만들고, 짧은 제한시간은 해당 유형에만 적용한다. 어려움을 골랐다고 스토리·주요 콘텐츠·꾸미기 아이템의 획득이 막히지 않는다.
   미니게임은 실제 법령 시험이나 실제 행정시스템 복제가 아닌 게임 내 설명된 가상 규칙을 바탕으로 한다. 실제 공무원이 아니어도 즐길 수 있어야 한다.
   실패하면 막히는 구조를 피한다. 재시도·되돌리기·힌트·정답 확인/보조 완료 등의 구조를 명세하고, 이미 획득한 보상을 중복 수령하지 못하게 한다.
3. 핵심 전환: 생활보장과 전체 맵 → 구역 선택/이동 → 화면 확대 → 퍼즐
   이번에 가장 중요하게 새로 확정할 시스템이다. ‘사무실 전체가 보이는 화면 하나 + 위에 팝업만 띄우는 구성’으로 끝내지 마라.
   생활보장과의 원본 14×21 배치 JSON을 기준으로 실제 책상·간부석·창구·프린터·캐비닛·회의 공간을 유지한다. 객체의 원본 footprint, 방향, 라벨을 보존한다.
   배치도에서 5~7개의 의미 있는 구역을 직접 도출하라. 예시 후보는 내 자리/PC·서류, 동료석, 계장·과장 결재, 민원 창구, 프린터·복합기·서고, 회의·휴식 공간이다. 예시는 확정 구역 경계가 아니며 실제 좌표에 맞춰 정하라.
   전체 지도에서 구역 또는 구역 내 목적물을 탭/클릭하면 선택 구역을 표시하고 캐릭터가 **장애물을 피하여 자동 이동(탭 투 무브)*한다. 이동 후 화면이 해당 구역 중심으로 자연스럽게 확대/이동한다. 모바일 사용자에게 매번 수동으로 캐릭터를 조종하게 만들 필요는 없다. PC 방향키 이동은 추후 선택 기능으로 비교한다.
   확대된 구역은 소품·동료·업무 버튼을 더 크고 명확하게 보여주고, 선택한 대상에 맞는 퍼즐 화면으로 이어진다. 퍼즐 완료 후 다시 해당 구역으로 돌아왔다가 전체 사무실로 복귀 가능해야 한다.
   전체 지도 ↔ 구역 확대 ↔ 업무 작업대/퍼즐 ↔ 결과 ↔ 구역/전체 지도의 상태 전이, 카메라 규칙, 뒤로가기, 선택 기억, 연속 업무, 줌 건너뛰기(동작 줄이기)를 설계하라.
   설계 문서에는 모든 구역의 이름·목적·정확한 좌표 경계(또는 다각형)·대표 포커스 지점·카메라 배율 목표·진입 핫스폿·접근 가능한 칸·연결 퍼즐·등장 NPC·꾸미기 슬롯을 표로 작성한다. 실제 소스 좌표에서 도출하라. 근거가 부족한 것은 설계 제안으로 구분한다.
   소스 JSON의 타일 좌표 → 월드 좌표 → 화면 좌표, 줌 배율/카메라 클램핑, 화면 중심 이동, 터치 판정 좌표, 접근 지점과 장애물의 구분을 명세한다. 시각적 책상 그림이 충돌 영역을 임의로 바꾸면 안 된다.
   길 찾기(BFS/A) 사용 여부·이동 실패 처리·가구 사이 좁은 통로·대상 접촉 반경·여러 오브젝트 중 어느 것을 먼저 누를지 판정 방식을 설계한다. 장면 전환 실패나 목표를 찾지 못한 경우를 대비한 ‘즉시 이동/업무 선택’ 대안을 마련한다.
   모바일의 세로 화면 320×640, 360×800, 390×844, 412×915와 PC 1280×800에서 지도, 확대, 버튼, 말풍선, 퍼즐 판정이 어떻게 표시되는지 와이어프레임으로 제시한다. 하단 UI와 OS 내비게이션 영역이 겹치지 않도록 안전 영역을 고려한다.
   픽셀 캐릭터가 확대되어도 흐릿해 보이지 않도록 정수 배율, 고해상도 텍스트 레이어, 구역 확대용 디테일 자산 중 적절한 방식을 선택한다. 화면이 작은 경우 카메라 확대와 스크롤 사이의 장단점을 비교해 기본값을 정한다.
   처음에는 실제 전체 자유이동 게임이 아니라 자동 이동·영역별 확대만 확실히 동작하는 구조를 우선 검증한다. 화면 이동에 따라 기존 퍼즐 진입·퇴근 흐름이 깨져서는 안 된다.
   실제 사무실 배치에서 가져온 정보는 외부 배포 시 안전·프라이버시 문제가 없는지 검토한다. 현실 인물·전화번호·민원 자료·실제 민감 문서는 가명/가상 데이터로 처리하고, 필요하면 공개 버전의 맵을 변형할 수 있게 한다.
   반드시 필요한 산출물: 구역별 명세, 맵 오버레이 시안, 메인→구역확대→퍼즐→되돌아오기 사용자 흐름도, 최소 3구역의 상세 화면 설계, 충돌·카메라·터치 구현 계획과 테스트 조건.
4. 신규 퍼즐 8종을 중심으로 생활보장과를 설계
   현재 구현된 5종 퍼즐을 버릴지 유지할지 막연히 넘기지 마라. 기존 유형은 튜토리얼/워밍업/업무의 일부 장치로 재사용, 새 버전에서 제안한 여러 해법이 가능한 퍼즐로 본편 재미를 확장하는 방향을 먼저 검토하라. 실제 플레이의 재미·난도·개발비에 따라 조정 근거를 남긴다.
   신규 본편 후보 — 반드시 8종 모두 설계
   결재 컨베이어 / 도장 공장 짓기: 레일·분기·복사·결재 도장 등 처리 장치를 격자에 배치해 목적별 서류가 올바른 결재함으로 흐르도록 한다. 복수 해법·최적화 기록.
   규정 개정 / 문장 타일: 게임 속 가상 규정의 단어·조건을 바꿔 여러 사례의 결과를 만족시킨다. 잠긴 상위 규칙·충돌 판정. 실제 법령을 임의로 고칠 수 있다는 의미가 아닌 풍자형 가상 규칙임을 명확히 한다.
   매크로 설계·디버깅: 받기·조건·중복 제거·합산·반복 등 블록 조합과 단계별 실행 로그, 경계값 입력·숨은 검증, 여러 정답. 초기에는 복잡한 반복/무한루프를 제한한다.
   서류 주인 찾기: 이름·시각·업무·서류 단서 등을 엮어 올바른 인물과 문서를 짝짓는 추리. 암기보다는 단서의 관계로 풀게 한다.
   결재 동선 짜기: 담당자 근무 가능 시간·선행 조건·결재 순서·마감으로 일정표를 구성한다. 합리적인 복수 정답 허용.
   서고 정리: 상자 밀기(소코반) 기반의 짧은 공간 퍼즐. 선택형 휴식/보너스로 두어 퇴근을 막지 않는다.
   예산 테트리스: 사업 기간×금액 블록을 월별·분기별 한도를 지키며 배치하는 턴제 공간 퍼즐. 빠르게 낙하하거나 줄을 없애는 일반 테트리스와 구별한다.
   한 장으로 줄여 와: 문장·정보 카드를 선택·결합해 필수 사실을 남기고 분량을 맞추는 요약·제약 퍼즐. 처음부터 AI 자유문장 채점에 의존하지 않는다.
   각 퍼즐에 대해 2~3개의 서로 다른 핵심 변형을 제시하라. 아래 항목을 개별 사양으로 반드시 채워라.
   플레이 목적, 현장 모티브, 시작 구역/오브젝트, 진입 대사, 조작법(터치/마우스/키보드), 처음 10초 튜토리얼
   화면의 모든 주요 요소·작업대 크기·버튼·피드백·완료(도장·서류 제출) 연출
   하/중/상 각각의 실질 규칙 차이와 예시 문제/정답/풀이 과정
   입력 데이터 스키마·출력 데이터 스키마·판정 함수 계약·복수해법/부분정답 허용 범위
   제한시간 또는 턴·힌트 3단계·실패/중도종료/되돌리기·재도전 규칙
   고정 문제 제작량/절차적 출제 가능 여부, 해가 존재함을 검증하는 방법
   퍼즐에 필요한 그래픽·사운드·UI 컴포넌트, 평균 플레이 시간, 최적화 점수 기준
   악용/무한 반복/정답 불분명/게임 진행 불능을 막는 테스트·완료 기준
   관련 도감 항목·성장 스킬·스토리 이벤트·꾸미기 보상과의 연결
   단순히 퍼즐명을 나열하지 말고 실제 구현 가능한 예시 스테이지를 포함한다. 8종을 한 번에 만들지 말고 기존 5종 → 핵심 A 3종 → B 3종 → C 2종 또는 분석 후 더 적절한 순서를 제시한다. 반드시 **플레이 가능한 세로 슬라이스(한 구역 확대 + 대표 퍼즐 1종 + 도장·스토리·보상·저장)**를 첫 검증 대상으로 정한다.
5. 게임의 세계관·스토리·등장인물까지 완성도 있게 설계
   퍼즐이 나열되는 것을 방지하기 위해 가벼운 스토리와 사건의 연속성을 포함한다. 예시는 다음과 같으며, 더 설득력 있는 안으로 개선할 수 있다.
   배경: 가상의 구청 생활보장과. 주인공은 새로 발령받은 주무관. 실제 특정 개인·부서의 사실관계를 재현하지 않는 코미디.
   제1막(첫 주, 1~5일): 첫 출근, 선배 소개, 기본 업무 도구, 서류·전화·결재의 세계 이해, 첫 퇴근.
   제2막(6~10일): 서식 변경·최종본 혼란·협조 요청·중간 마감이 겹침. 고급 퍼즐과 동료별 작은 사건 도입.
   제3막(11~15일 또는 후속 장): 예산·업무보고 시즌과 돌발 요청. 도구 및 동료의 도움을 조합해 ‘금일 중 제출’의 큰 사건 해결. 1회성 감동 교훈 대신 공감되는 건조한 유머로 마무리.
   날마다 시작하는 구청 소식/게시판에 전날 결과·새 규칙·오늘의 사건이 나타나고, 종료 시 근무 기록/영수증에 처리한 일과 다음 날 예고가 나온다.
   주인공의 성장은 일을 더 많이 떠맡는 것이 아니라 같은 일을 현명하게 처리하고 여유·꾸미기·관계를 얻는 데서 느껴야 한다.
   인물은 실명 대신 가상의 선배·담당 동료·계장·과장·타과 협조 담당자 등을 작은 규모로 구성한다. 각 NPC의 성격·업무·대사 말투·처음 등장·반복 이벤트·관계 변화·관련 퍼즐·대화 조건을 설계한다. 관계가 나쁘다고 게임을 영구히 못 깨는 구조는 금지한다.
   요구 산출물: 3막 구성표, 최소 15일의 핵심 진행표(그날의 새 사건·퍼즐·해금·대사·보상), 가벼운 선택지/플래그 체계, 되돌아오는 결과 10개 이상, 대표 대사와 퀘스트 텍스트 샘플(첫 출근·서식 변경·최종본 혼란·점심시간 순삭·결재 반려·타과 협조), 엔딩/엔딩 이후 반복 모드. 새 스토리 회차에서도 반복 퍼즐과 충돌하지 않게 한다.
   풍자의 중심은 악성 요구, 촉박한 제출, 불합리한 절차, 파일명 혼란, 반복 수정 등 행정의 상황으로 한다. 복지 대상자나 민원인의 약한 처지를 웃음거리로 만들지 않는다. 과한 교훈·훈계·무조건적인 미담 결말은 피한다.
6. 성장·꾸미기·도감·수집을 ‘형식상 메뉴’가 아니라 플레이 시스템으로
   기존 코드의 성장 도구, 책상 꾸미기, 업무 도감을 상세한 기획으로 확대하라. 처음부터 모두 구현하는 것이 아니라 필요한 데이터 구조와 최소 버전을 먼저 마련한다.
   성장
   경험치, 직급/칭호, 부문별 숙련도(검토/추리/자동화/조율 등), 도구 해금 규칙.
   숫자만 오르는 능력치보다 메모 보조, 힌트, 비교 강조, 동료의 회신 대기 단축, 실수 복구, 일부 쉬운 반복 처리 등 실제 조작 변화.
   쉬움/보통/어려움의 보상 격차가 스토리·도감 완성을 막지 않게 한다.
   개발 초기 기본 포인트 경제: 1일차~15일차 예상 수입과 소비, 소품·도구 가격, 중복 파밍 방지, 유료 재화 없음.
   꾸미기
   내 책상을 시작으로 화분·머그컵·문구류·스탠드·의자 커버·모니터 테마·결재 도장·벽 포스터 등 소품.
   **구역별 장착 슬롯/부착 지점(anchors)**을 원본 가구와 분리하여 정의. 자유 배치는 MVP에서 제외 또는 후순위로 검토.
   구매·해금·장착·교체·미리보기·수집/미보유·포인트 부족·중복 구매·저장·화면 반영 방식을 명세.
   상호작용 확대 화면에서 소품이 실제로 보이도록 한다. 의미 없는 아이콘 목록만 늘리지 않는다.
   업무 효율에 영향을 주는 성장 도구와 순수 외형용 꾸미기 소품을 명확히 구별한다.
   도감과 수집
   업무 도감: 퍼즐 유형·완료 기록·최고 기록·해금 일자·힌트 사용 등.
   인물 도감: 등장 NPC·관계 이벤트·작은 일화.
   소품 도감: 획득한 장식·세트 보너스(가급적 외형용)·배치 보기.
   구청 지도/부서 도감: 생활보장과와 이후 타과 협조 도장/배지·부서 고유 퍼즐 기록.
   사건·업적 도감: 최종_진짜최종 같은 웃픈 사건, 특정 도구로 처리한 첫 업무, 정시퇴근 기록 등.
   숨겨진 수집 요소는 안내와 사후 힌트로 찾을 수 있게 한다. 플레이 횟수를 강요하는 무의미한 노가다는 지양한다.
   요구 산출물: 도구 8~12종 제안, 소품 12~20종 후보와 MVP 우선순위, 도감 카테고리·아이템 데이터 예시, 최소 15개 업적 예시, 획득→저장→장착→화면 적용 플로우, 포인트 경제 및 밸런싱 기준, 예상 UI 와이어프레임.
7. 생활보장과 완성 뒤 타과로 확대하는 시스템 설계
   타과는 생활보장과의 핵심 흐름이 대강 완성되고 회귀 테스트를 통과한 뒤 추가한다. 지금 당장 11종 전부를 구현하지 마라. 단, 초기에 다른 부서도 같은 엔진에 연결할 수 있는 콘텐츠 구조는 반드시 준비한다.
   공무원키우기_새버전_기획시안.html에 있는 타과 퍼즐 후보를 누락 없이 추출·분류하라. 주요 후보:
   자원순환과 — 재활용 선별장 (물 정렬)
   상하수도사업소 — 상수도관 연결 (경로 연결)
   교통행정과 — 불법주차 견인 작전 (화살표 제거 순서)
   토지정보과 — 지적도 복원 (노노그램)
   기록관리팀 — 기록물 철하기 (트리플 매치)
   재난안전과 — 구호물자 창고 정리 (상자 밀기)
   문화관광과 — 축제 부스 배치 (블록 배치)
   하천관리과 — 장마철 수문 관리 (핀·유체 단순화)
   공원녹지과 — 노후 놀이터 해체 (나사·판자 퍼즐)
   건축과 — 현장 안전점검 (위험 요소 찾기)
   정보화팀 — 정산 매크로 만들기 (본편 매크로와 공통 엔진 공유)
   확장 구조의 방향: 부서 ID / 부서 명칭 / 맵 또는 구역 / 업무·퍼즐 유형 / 난이도 설정 / 해금·보상 / 담당 NPC / 도감·꾸미기 / 이벤트 / 의존 에셋을 데이터팩 단위로 분리한다. 핵심 엔진과 저장 기능을 수정하지 않고 새 부서 데이터팩·퍼즐 모듈을 등록하면 추가될 수 있도록 설계한다.
   타과 진입 동선은 예를 들어 생활보장과 업무함의 협조 요청 → 청사 지도 → 해당 부서(가상 구역) → 퍼즐 → 부서 우호도·도감 스탬프 → 생활보장과로 복귀로 설계한다. 타과 업무는 초기에는 선택적 협조로 두며, 본업의 퇴근 조건을 막지 않는다.
   각 부서 퍼즐에 대해 참고하는 일반 퍼즐 메커닉 / 공무원 업무로 바꾼 독창 요소 / 예시 문제 / 개발 난이도 / 재사용 가능한 엔진 / 새로운 자산량 / 우선순위 / 도감 보상 / 본편에 주는 작지만 의미 있는 효과를 표로 작성한다.
   1차 후보: 격자 시스템을 재사용할 수 있는 재활용 선별장·상수도관 연결·불법주차 견인·지적도 복원. 2차: 기록물 철하기·구호물자·축제 부스·정산 매크로. 3차: 수문·놀이터·안전점검. 실제 분석으로 순서 변경 가능하지만 이유를 남겨라. 타사 게임의 이름·그래픽·문제·UI를 그대로 복제하지 않는다.

   설정(난이도 상·중·하, 소리, 동작 줄이기, 텍스트 크기)
   저장·내보내기·가져오기·새 게임·오류 복구
   각 화면마다 와이어프레임(텍스트·ASCII·SVG 중 효율적 방식), 정보 우선순위, 버튼 상태, 뒤로가기/중단/복구, 터치 영역, 색상·글꼴, NPC/오브젝트 이미지 자산을 명세하라. 실제 퍼즐에 필요한 숫자는 이미지에 굳히지 말고 HTML 텍스트로 넣어 가독성과 수정 가능성을 유지한다. 장치·도장·종이·전화 등의 효과음은 저비용 자체 제작/생성 방식을 우선 검토한다.
9. 아키텍처·저장·성능·개발 방식
   먼저 공무원키우기_픽셀아트.html을 실제로 구조 파악하고, 재사용 가능한 순수 게임 규칙 코드와 UI/렌더/에셋/사운드/저장 코드의 결합 상태를 평가한다.
   기존 규칙과 데이터를 GameCore 유사 공통 로직 / PuzzleRegistry / PuzzleModule / QuestionData / DepartmentPack / ZoneMap / CameraController / Movement / EventNarrative / Progression / Economy / Inventory / Codex / SaveRepository / Renderer` 등 역할 단위로 분리하는 방법을 제안하라. 이 이름은 예시이며 실제 파일 이름은 적절히 정해라.
   기술 스택은 현재 HTML·CSS·JavaScript의 재사용성과 Android 브라우저 동작을 우선 고려한다. Phaser/Godot로의 전면 재작성은 측정 가능한 이득이 재작성 비용보다 클 때만 선택하고, 근거를 비교 표로 설명하라.
   개발 중 소스는 모듈로 나누되, 배포 시 외부 네트워크 없이 여는 단일 HTML 또는 정적 로컬 웹앱으로 번들할 수 있는 구성을 권장한다. 필요하다면 번들러·테스트 러너를 선정하고 실제 실행 명령을 계획서에 적어라.
   Android 삼성 브라우저의 content:// 또는 로컬 파일 실행, 로컬스토리지 제한 가능성, 브라우저 데이터 삭제, 저장 실패, 화면 회전, 뒤로가기, 터치 처리 등에 대해 확인할 사항과 폴백 동작을 설계한다. 확실하지 않은 플랫폼 동작을 보장이라고 쓰지 마라.
   세이브 v1 → 확장 v2/v3 스키마, 기존 이름·경험치·포인트·도구·꾸미기·업무기록 보존·마이그레이션·롤백·JSON 백업을 상세히 설계하라. taskId별 보상 1회, 중도 저장된 퍼즐 상태·seed와 난이도 불변, 일차와 스토리 플래그, 구역·카메라 선택 상태의 저장 범위를 명확히 한다.
   문제는 데이터로 추가할 수 있게 하되, 신규 퍼즐의 판정기는 게임 로직과 분리하라. 퍼즐에 복수 정답이 있으면 결과 상태가 맞는지를 판정하고, 가능한 경우 해법 존재성 검증/고정 테스트 세트를 제공하라.
   주요 기능은 단위 테스트 + 스테이지 전체 자동 시뮬레이션 + UI E2E(가능한 환경) + 실제 Android 브라우저 확인 체크리스트로 검증한다. 테스트 환경이 없다면 ‘미검증’으로 표시하고 대체 테스트를 명시한다.
   유사 사례 및 아트 참고는 라이선스·출처 표기 지침을 따른다. 외부 유료 API·무단 스크래핑·타사 저작물 포함을 기본 전제로 하지 마라.
10. 단계별 로드맵 — 구체적인 TASK와 검증 게이트
    최소 다음 마일스톤으로 분리하되, **각 단계마다 ‘체험 가능한 빌드’**를 만드는 것을 원칙으로 한다.
    P0 현황 진단·결정표: 첨부자료 기능 검증, 충돌 정리, 기술 선택, 원본 백업/변경 금지 계획.
    P1 게임 핵심 규칙·데이터 계약: 세이브 버전·스토리 플래그·퍼즐 등록·부서팩·도감·인벤토리 데이터 모델 설계.
    P2 맵·카메라 세로 슬라이스: 실제 14×21 맵, 3개 구역, 탭→자동 이동→확대→업무→복귀. 이 단계에서 구역 설계의 재미와 화면 가독성을 먼저 검증.
    P3 핵심 퍼즐 세로 슬라이스: 결재 컨베이어 또는 설득력 있는 대체 퍼즐 1종, 하/중/상, 도장 손맛, 결과, 저장.
    P4 1주차 플레이 완성: 출근 소식지·4건 업무·선택 대기·결산·동료·튜토리얼·기존 5종의 재사용 방침 실행.
    P5 신규 논리 퍼즐 A군: 결재 컨베이어·규정 개정·매크로 디버깅, 검수된 고정 스테이지.
    P6 성장·스토리·꾸미기·도감: 서사 1~2막, 도구/소품/업적, 내일 결과, 포인트 경제, 세이브 마이그레이션.
    P7 신규 퍼즐 B군: 서류 주인 찾기·결재 동선·선택 서고, NPC·작업대 연출 연결.
    P8 신규 퍼즐 C군·생활보장과 베타: 예산 테트리스·한 장 보고, 3막, 15일 내외 진행, 밸런싱.
    P9 베타 안정화: 모바일·PC 회귀/저장/성능/가독성·빌드·피드백 반영.
    P10 타과 확장 1차: 4개 격자 퍼즐 기반 부서팩·청사 지도·부서 도감 스탬프. 생활보장과 베타 안정화 이후 실행.
    P11 타과 확장 2·3차: 반응과 검수 결과에 따라 선택.
    각 마일스톤 아래 TASK-ID, 우선순위(P0/P1/P2), 목적, 사전 조건, 구현 상세, 수정할 파일·모듈, 입력 데이터, 산출물, 자동 테스트 항목, 수동 QA 절차, 실패·예외 대응, 완료 조건(Definition of Done), 예상 난도, 다음 작업 의존성을 빠짐없이 작성하라. 한 TASK는 가급적 독립된 소규모 코드 변경과 테스트로 끝날 수 있도록 쪼갠다. 기획 단계에서 날짜나 개발시간을 근거 없이 확정하지 마라. 가용 작업량 불명확하면 상대적인 난도/작업량을 제시하라.
    특히 P0~P3는 가장 상세하게 작성하여, 별도 구두 설명 없이 구현자가 시작할 수 있도록 한다. P4~P9는 기능별 완료 조건과 테스트까지, P10 이후는 재사용 구조와 대표 업무까지 상세히 설계한다. 내가 나중에 결정처럼 핵심 결정이 비어 있으면 안 된다.
11. 품질 기준 / 반드시 통과할 검수 목록
    생활보장과 14×21, 원본 물품 46개 좌표·크기·방향 보존 및 영역 밖/가구 겹침 검수.
    대표 업무 구역에 탭으로 도달 가능하고, 이동과 확대에서 UI가 끊기지 않으며 현재 위치·뒤로가기가 일관됨.
    320px대 세로 화면과 390px대 세로 화면에서 글자가 읽히고 핵심 조작 버튼을 누를 수 있음. 퍼즐은 잘려 있지 않음.
    구역 확대·퍼즐 완료·꾸미기 적용·도감 갱신·퇴근 후 다음 날·저장 복구가 한 사이클로 연결됨.
    각 퍼즐에 해가 있으며 같은 결과를 만드는 복수 정답을 허용하고, 잘못된 답의 원인을 안내.
    퍼즐 종료·새로고침·뒤로가기·작업 중 저장/복원·중복 완료 보상·게임 진행 불능을 검증.
    하/중/상 모두 진행 가능, 난이도 변경 시 다음 신규 퍼즐부터 일관되게 적용. 난이도 차이로 핵심 콘텐츠 잠김 없음.
    기존 저장 데이터 테스트 픽스처로 마이그레이션을 검증하고, 사용자 진행 상태를 잃지 않음.
    실제 민원인·공무원 개인정보가 테스트 데이터나 게임 자산에 들어가지 않음.
    타과 퍼즐을 샘플 부서팩 하나만 등록해도 메인/도감/보상/저장이 동작하도록 확장 가능성을 검증.
    외부 리소스 미로딩·오프라인·오래된 모바일 브라우저·동작 줄이기 사용 시에도 치명적인 오류가 없음.
    플레이가 재미없을 위험(업무 재현에 치우침, 매번 같은 문제, 긴 애니메이션, 도구가 주는 무의미한 보너스)을 발견하고 실제 수정 방향·측정 방법을 제시.
