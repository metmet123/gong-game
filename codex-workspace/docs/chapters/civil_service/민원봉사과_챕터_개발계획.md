# 공무원 키우기 민원봉사과 챕터 개발계획

계획 v1.0 · 2026년 10월 11일 · 구현 상태 planned

민원봉사과를 인사발령으로 시작하는 두 번째 근무 챕터로 만든다. 중심 이야기는 **반복 방문의 원인을 찾아 창구 안내와 자료 전달을 개선하는 10일**이다. 새 민원실, 새 동료 5명, 주요 방문자 4명, 하루 4건의 업무와 후속 회신을 연결한다. 첫 산출물은 1~3일의 12건을 끝까지 플레이하는 체험판이며, 기존 퍼즐 7종을 재사용하고 공개 범위 검토 퍼즐 1종을 추가한다.

이 수량·일정·좌표·이름·대사·금액은 게임용 개발 제안이다. 실제 기관의 업무와 사건은 아래 출처 범위에서만 참고한다. 공개 자료를 게임에 넣는 목적은 절차와 맥락을 이해하는 것이며, 실무용 서식이나 법률 판단 서비스를 제작하는 것이 아니다.

## 1 현재 구현과 이번 개발 범위

사용자가 제시한 [현재 배포본](https://metmet123.github.io/gong-game/)의 연습실에는 기존 5종, 머리 퍼즐 8종, 부서 미니게임 11종이 플레이 가능으로 표시된다. 앞선 확인에서 규정 개정 작업 화면을 열었으나 24종 전체의 판정·저장·캠페인을 검증하지는 않았다. 작업 폴더의 game-core.js와 기존 HTML은 배포본과 같은 버전이라고 가정하지 않는다.

착수 시 최신 배포 소스의 커밋과 빌드 입력, 저장 구조, 퍼즐 registry, 지도 renderer를 먼저 확인한다. 새 챕터를 과거 build_scene.py로 생성하면 기존 HTML들을 덮어쓸 수 있으므로 해당 생성기는 실행하지 않는다. 생활보장과 원본 맵과 기존 narrative 데이터는 보존하고 새 chapter namespace에 작성한다.

|항목|첫 3일 체험판|10일 본편|
|---|---|---|
|필수 업무|12개 업무 맥락, 쉬움 12문제|40개 업무 맥락, 하·중·상별 1변형씩 총 120문제 변형|
|퍼즐 종류|재사용 7종과 신규 1종|같은 8종 유지|
|지도|24×18 민원실 한 장, 논리구역 8개|동일 지도에 안내·야간·전시 변화|
|새 동료|3명 실제 대화, 나머지 2명 이름과 위치 소개|5명 모두 관계 일화|
|주요 방문자|이다정·진해솔 2명|4명|
|주요 사건|세 번째 방문 1개, 사진·여권 서브 사건 시작|연속 사건 4개|
|아이템|개인 소품 6개와 기본 업무도구 4개|개인 소품 12개와 업무도구 4개|
|원본 저장|사본 fixture와 새 시험키|최신 저장에 검증된 챕터 확장 적용|
|완료 기준|발령부터 3일 퇴근까지, 사건 해결·초안·복원|10일 결산, 관계·공개 검토·다음 발령 인계|

체험판의 중·상은 준비 중으로 표시하고 눌렀을 때 쉬운 문제로 몰래 바꾸지 않는다. 120은 40개 맥락의 난도별 변형 수이며, 서로 독립된 이야기 120편 또는 구현 완료 수가 아니다. 본편의 선택 업무는 하루 최대 1개, 무보상 연습은 별도다.

현실의 야간 운영 요일·수수료·기한을 전국 공통값으로 사용하지 않는다. 게임은 날짜선택용 정수 슬롯과 가상의 업무 조건을 보여준다. 이름이 들어간 정보라고 모두 비공개라는 규칙도 쓰지 않는다. 공개 범위는 문서별 공개 검토표를 근거로 판단한다.

## 3 인사발령과 하루의 진행

생활보장과의 사용자 선택 가능한 챕터 결산 뒤 인사발령 안내를 보여준다. 현재 배포본의 실제 엔딩 조건은 첫 착수 작업에서 확인한다. 엔딩이 없는 버전이라면 임의의 15일 조건을 강제로 덧붙이지 않고 개발용 챕터 진입 버튼으로 먼저 시험한다.

발령 장면은 발령장 열기 → 나소라와 인수인계 → 가져갈 개인 소품 확인 → 시간 경과 → 새 청사 1층 민원실 도착이다. 챕터 변경은 다음 근무 시작을 확정할 때 저장하며, 장면 도중 종료해도 이전·다음 상태 중 검증된 한 상태로 복원한다. 가져갈 소품 선택을 취소해도 소유품이 사라지지 않는다.

일과는 소식지 → 창구 또는 책상 선택 → 요청과 공개 규칙 → 편집 → 확인 → 제출 → 주민 반응 → 사무실 복귀 → 4건 후 퇴근 순서다. 하루 목표는 6~10분이며 쉬운 일 2개, 핵심 사건 1개, 회신·정리 1개로 길이를 조절한다. 강제 실시간 대기·실패 제한·반응속도 채점은 넣지 않는다.

여권 업무 완료는 접수 검토·교부 등 해당 단계의 완료다. 접수한 즉시 주인공이 여권을 제작하거나 발급 승인하는 장면은 넣지 않는다. 보완이 필요한 민원도 올바른 보완 안내를 마치면 업무 완료가 될 수 있다.

## 4 민원실 맵과 이동

새 맵은 가상의 24열×18행, 좌표는 0부터 시작한다. 평면 직교 격자와 기존 픽셀 표현을 사용하며 전면은 주민 공간, 후면은 직원 책상, 오른쪽 후면은 기록 구역이다. 중앙 x12~13은 주 통로로 보존한다. 구조화한 30개 물품과 5칸 칸막이는 map_layout.json에 있다.

|구역|주요 물품|업무와 의미|
|---|---|---|
|Z01 접수 안내|안내대·번호표·서식대|목적 확인, 올바른 창구·자료 안내|
|Z02 통합 증명|통합 창구·주인공 책상|서류 대조, 종류와 범위 비교|
|Z03 여권 접수와 교부|접수 창구·검토 책상·별도 교부대|접수자료 검토, 사진 보완, 교부 대상 매칭|
|Z04 가족관계|신고 창구·담당 책상|공개된 사례 기준에 따른 신고서 검토·후속 안내|
|Z05 정보공개|접수 창구·공개 검토 책상|자료 범위·가림 처리·검토 회신|
|Z06 기록|자료장 2개·열람 작업대|연도·버전·문서 성격에 맞는 자료 찾기|
|Z07 대기와 상담|대기석·기기·상담석·전시대|주민과 대화, 도움 제공, 개선 결과 확인|
|Z08 직원 지원과 출입|팀장석·인계함·출력·파쇄·급수·게시판·출입|결재·휴식·결산·챕터 이동|

각 물품의 footprint는 충돌 계산에 사용하고 interactionCell은 인접한 비점유 칸으로 따로 둔다. 구역은 카메라의 관심 영역이며 통행을 막는 사각형이 아니다. 칸막이 x17,y0~4를 지나지 않고 y5의 출입구로 기록 구역에 접근한다. 번호표 발권기는 열람 장치이며 실제로 여러 주민을 실시간 처리하는 별도 대기열 시뮬레이터는 첫 버전에 넣지 않는다.

첫 체험판에서는 주인공만 장애물을 회피해 이동한다. 주민은 창구 앞 또는 대기석의 예약 위치에서 나타나므로 길을 막지 않는다. 직원 전용 구역은 방문자 이동 그래프에서 제외하고, 주인공은 양쪽에 접근한다. 실제 플레이에서는 주민의 접근점과 주인공의 접근점을 구별한다.

|카메라 상태|화면 구성|복귀와 조작|
|---|---|---|
|전체 민원실|지도와 대기 업무 4개, 주요 목표|물품 선택 시 경로 표시 후 이동|
|창구 확대|주민 초상·요청 카드·자료 열기|뒤로는 전체 민원실|
|퍼즐 작업대|목표·자료/작업/확인·하단 조작|뒤로는 초안 저장 후 해당 창구|
|제출 결과|완료 단계·후속 약속·보상|현재 구역으로 복귀|

모바일 전체 지도는 축소하고 물품 목록 버튼으로 같은 대상에 접근한다. 작업대 텍스트는 DOM으로 표시한다. 320px에서 드래그 없이 카드 선택→칸 선택으로 완료 가능해야 한다. 큰 글씨, 무음, 동작 줄이기에서도 같은 판정을 쓴다.

지도 변화는 3일 안내판 갱신, 6일 야간 조명과 창구 표시, 9일 공개 자료 전시, 10일 인계함이다. 통로와 고정 가구는 유지하고 새 장식이 접근점을 덮지 않게 한다. map_preview.svg는 배치 계획 그림이며 최종 게임 아트가 아니다.

## 5 캐릭터와 관계

새 동료 5명은 가상의 인물이다. 기존 캐릭터 ID를 바꾸지 않고 cs 접두사가 있는 새 ID를 등록한다. 한 캐릭터가 두 업무를 지원할 수 있지만 신규 주무관이 모든 전문 업무를 독자적으로 처리하는 설정은 피한다.

|인물과 역할|성격과 첫 대사|관계의 변화|첫 체험판|
|---|---|---|---|
|서유진 민원행정팀장|차분하게 업무를 나눔. “모르면 붙잡고 같이 보면 돼요.”|개별 처리→원인 보고→인계 신뢰|1일 소개, 3일 피드백|
|문도현 통합 증명 담당|짧고 정확한 설명을 좋아함. “무슨 서류인지보다 어디에 쓸 건지부터요.”|질문 연습→안내문 공동 수정→새 직원 교육|핵심 동료|
|오세린 여권 담당|체크판에 작은 메모를 남김. “사진은 기억보다 기준표가 정확해요.”|검토 도움→야간 창구 협업→교부날 안부|핵심 동료|
|고은결 가족관계 담당|기쁜 일도 어려운 일도 조용히 응대함. “다음 절차까지 적어드릴게요.”|신고서 검토→후속 안내→개인 취향 일화|이름·위치 소개|
|정이안 기록과 공개 지원|자료의 출처를 묻는 습관. “가릴 부분과 남길 부분을 같이 봐요.”|찾기→공개 검토 협조→전시 기록|3일 문서 메모로 등장|

관계는 특정 동료 관련 고유 업무 완료 1·3·5건에 일화 1·2·3을 연다. 난도·실수·보조 완료에 관계없이 열리며 반복 연습으로 횟수를 올리지 않는다. 같은 날 자동 대화를 많이 쌓지 않고 일화는 선택 메뉴에 보관한다. 새 일화는 동료당 3개, 총 15개다.

|주요 방문자|요청과 생활 맥락|연속 등장|
|---|---|---|
|이다정|지역 프로그램 제출 서류를 준비하며 안내의 표현에 혼란을 겪음|1·2·3·9일|
|진해솔|첫 해외 일정에 앞서 여권 접수와 수령 방법을 확인함|2·4·6일|
|홍서우|혼인 신고 관련 자료와 이후 주소 변경 안내를 받음|4·5·10일|
|배한빛|민원실 편의시설 개선 기록을 확인하고 싶어 함|3일 청구 메모, 7·8·9일|

거주지·가족관계·장애·건강 상황을 희화화하거나 민원인을 방해물로 점수화하지 않는다. 이야기의 갈등은 이해하기 어려운 안내, 서로 다른 자료, 협조 지연과 실제 생활 일정에서 만든다.

기존 인물의 연결은 나소라 0일 발령과 5일 안부, 연미루 1일 복합 요청 전화, 백단비 7일 기록 협조, 임하루 2·8일 부서 회신 전달이다. 등장 조건을 과거 선택 업무 완료로 강제하지 않는다. 과거 관계가 있으면 친숙한 대사, 없으면 첫 인사 대사를 쓴다.

## 6 네 연속 사건과 후속 결과

E01은 첫 3일 안에 해결한다. E02는 여권 보완과 교부, E03은 신고와 후속 안내, E04는 공개 준비와 보완 회신을 각각 분리한다. 여러 민원이 섞여 있다는 이유로 모두 정보공개 청구로 취급하지 않는다. 자료 열람 요청과 서비스 개선 건의가 한 편지에 있으면 두 처리 항목을 같은 사건에 연결한다.

첫 3일의 핵심 대사 예시:

- 1일 이다정: “안내에 적힌 서류는 가져왔는데, 다른 걸 떼 오라고 하셔서요.”
- 1일 문도현: “오늘 필요한 범위를 여기 함께 표시해 볼까요?”
- 2일 임하루: “옛 안내문이 아직 다른 창구에도 남아 있었대요.”
- 3일 이다정: “오늘은 제가 어느 칸을 봐야 하는지 알겠어요.”
- 3일 서유진: “한 건을 끝낸 것도 좋지만, 다음 사람이 덜 헤매게 된 게 더 좋네요.”

설명 방식의 선택지는 요약 먼저 / 자료를 함께 보며 설명으로 두고 두 방식 모두 필수 처리가 가능하다. 선택은 replyStyle 플래그와 후속 대사에 반영한다. 행정상 보완을 없애거나 필요한 확인을 건너뛰는 선택으로 호감 보상을 주지 않는다.

### 신규 공개 범위 검토

목표는 공개 검토를 통해 필요한 정보가 담긴 공개 사본을 만드는 것이다. 주인공은 검토표를 적용하는 자료 준비 담당이며 최종 공개 결정은 담당자 확인 이벤트와 연결한다. 검토표에 없는 법적 예외를 숨은 채점 조건으로 추가하지 않는다.

작업은 문서 토큰 선택 → 보이기/가리기 → 이유 카드 선택 → 확인이다. 정답이면 제출 버튼을 활성화한다. 수정하면 유효 평가를 해제한다. 오류 클릭 시 해당 토큰으로 이동하고 초안은 유지한다. 전체 비공개/전체 공개 버튼으로 무조건 통과할 수 없다.

|대표 문제|가상 문서와 검토표|유효 초안|실패 예|
|---|---|---|---|
|하 cs.disclosure.e01|창구 개선 보고의 목적·금액·업무담당 직위·사적 연락처. 앞 3개는 공개 유지, 연락처만 가림|show/show/show/hide, 연락처 사유 private_contact|전화 노출, 금액 가림, 미검토 남김|
|중 cs.disclosure.n01|개선 의견서 6토큰. 의견과 조치·날짜는 공개, 별명과 세부 주소는 단독·결합 식별 가능하다고 검토표에 명시|검토표 지정 보호 토큰 2개를 가리고 나머지 유지|이름만 가리고 상세 위치를 남김, 의견까지 가림|

e01의 완전한 계획 fixture는 chapter_plan.json의 disclosureExample에 포함한다. 입력 tokens는 id·text·factId·policy(show/hide)·allowedReasons, constraints는 requiredFacts·documentIds, 초안은 tokenStates와 reasonByToken이다. policy는 제작 데이터이며 UI에서는 정답 태그 대신 검토표 문장으로 제공한다.

순수 판정 순서는 알려진 문서·토큰인지 → 모든 필수 토큰 검토 여부 → 가림 사유의 적법성 → 보호 토큰 노출 여부 → 공개 필수 사실 보존 → 요청 문서의 누락 여부다. 이유 코드는 unknownToken/unreviewed/protectedVisible/requiredFactHidden/wrongReason/missingDocument로 구분한다. 출력은 status·reasons(targets)·metrics(가린 수/검토한 수)·facts다.

아직 미검토한 항목은 incomplete, 확인한 항목에서 보호·공개 조건을 어기면 invalid다. 도움1은 관련 검토 기준, 도움2는 실패 항목과 사유, 도움3은 한 유효 초안을 준다. 보조 완료도 핵심 보상은 같다. 문서에 임의 HTML이나 외부 URL을 실행하지 않는다.

## 11 챕터 데이터와 저장 구조

진행은 전역 경력과 챕터별 근무를 분리한다. 전역에는 profile·XP/P·ownedItems·관계·업적, 챕터에는 chapterId·day·phase·tasks·drafts·eventLedger·mapState·returnContext를 둔다. 정확한 필드명과 버전은 최신 배포본의 저장 확인 뒤 결정한다.

ChapterPack은 맵·동료·일차·사건·퍼즐 adapter·아이템·출처를 참조한다. 새 엔진 disclosure는 registry에 등록하고 기존 제출·보상·초안 흐름을 사용한다. 콘텐츠에 임의 script를 넣지 않는다. 오프라인 실행에는 서버·AI API·실시간 검색이 필요하지 않다.

## 12 콘텐츠 데이터 제작 계약

chapter_plan.json은 40개 업무와 원형 설계를 담은 계획 데이터이며 실행 가능한 완전 stage 120개를 대체하지 않는다. 각 stage 제작 시 publicRules·input·goals·constraints·initialDraft·hintSteps·witness·contentVersion을 작성한다. 법정 수수료·번호·실명 대신 가상 정수와 가명 문서를 사용한다.

사건은 condition→scene→task→completionEffect→callback으로 나눈다. completionEffect의 허용 항목은 flagSet·nextTaskReady·relationOnce·itemClaim·mapVisual이다. 대화 종료만으로 필수 업무가 완료되지 않으며, 이미 완료된 task callback을 새로고침마다 실행하지 않는다.

반복 업무의 난도는 날짜 진행이 아니라 사용자 설정에 따른다. 장면의 담당자·문서 목적·보완 결과는 난도와 무관하게 이어진다. 40개 업무×3난도에 대해 해 존재와 내용 검수를 따로 기록한다. 몇 가지 witness의 통과만으로 전체 콘텐츠 완성이라 보고하지 않는다.
