# 공무원키우기 문서 역할과 담당

문서 관리 방식은 사용자 전역 지침을 따르고, 이 목록은 기존 파일의 역할과 담당을 연결한다. 파일명만으로 실행 계획, 확정 명세와 작업 로그를 같은 문서로 취급하지 않는다. 경로는 프로젝트 루트 기준이다.

## 공통 운영 문서

| 문서 | 역할 | 담당 |
| --- | --- | --- |
| [PROJECT](PROJECT.md) | 프로젝트 목적과 섹션 구성 | 확장계획 |
| [SPEC](SPEC.md) | 공통 규격과 통합 기준 | 확장계획 |
| [OWNERS](OWNERS.md) | 파일 담당과 기존 경로 예외 | 확장계획 |
| [공통 운영 작업 로그](2._WORK_LOG.md) | 폴더 구성과 지침 등 공통 운영 작업의 실제 결과 | 확장계획 또는 사용자가 지정한 운영 작업 담당 |
| 각 섹션의 STATUS.md | 현재 상태, 수정 범위, 다음 작업과 전달 확인 | 해당 섹션 |
| [전달 기록](handoffs/README.md) | 다른 섹션에 필요한 변경과 조치 | 각 발신 섹션 |

공통 운영 로그는 섹션의 게임 개발 로그를 대체하지 않는다. 실제 작업 결과를 기록할 동등한 로그가 없는 섹션은 해당 개발 작업에서 로그 생성 범위를 정하고 자기 폴더에 만든다. 같은 정보를 여러 로그에 반복 기록하지 않는다.

개발진행 문서는 현황과 이전 검증이 섞인 기존 문서이며 자동으로 전체를 작업 로그로 재분류하지 않는다. 결과 기록과 현황이 혼재하면 담당이 현재 상태를 유지하고 상세 이력을 로그로 연결한다.

## 활성 계획과 미완료 목록

현재 문서 정리 작업에서는 PROJECT_PLAN.md, 3._TODO.md와 섹션별 신규 로그를 일괄 생성하지 않는다. 기존에 같은 역할을 하는 문서가 있으면 사용하고, 별도 활성 계획이나 미완료 목록이 필요한 작업에서 생성 범위를 정한다.

새 활성 실행 계획을 만드는 경우 목표, 상태, 완료, 진행, 결정, 검증으로 구성하고 확정 명세와 상세 결과는 해당 문서를 링크한다. 완료된 실행 계획의 상세 경과는 로그에 옮기되 기존 명세, 승인된 시안과 완료 기준은 보존한다.

## 상태 문서와 기록의 소유권

섹션의 STATUS는 소통용 현재 요약이며 다른 섹션의 담당이 완료 처리하지 않는다. 문서 형식을 정리하는 운영 작업에서는 기존 구현 상태와 미확인 전달을 유지한다. 다른 채팅이 지침을 읽거나 검증을 완료했다고 대신 기록하지 않는다.
