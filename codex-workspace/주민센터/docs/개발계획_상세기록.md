# 주민센터 전입신고 챕터 상세 개발계획

계획 버전 1.0 · 2026년 10월 11일 · 개발 책임 Codex · 단계별 구현은 아직 예정

주민센터의 업무 퍼즐과 이야기를 전입신고 하나로 구성한다. 첫 목표는 모바일에서 여섯 사례를 끝까지 플레이하고 중간에 종료해도 이어 할 수 있는 독립 퍼즐이다. 그다음 인사발령, 주민 재방문, 새로운 주민센터 맵, 기존 인물과의 연결을 붙인다. 현재의 화면 시안은 출발점이며 완성된 퍼즐이나 챕터로 간주하지 않는다.

사용자가 매 작업의 세부 결정을 내릴 필요가 없도록 이 문서의 기본값, 사례 계약, 작업 순서, 통과 조건을 개발 기준으로 사용한다. 여기서 정한 로컬 구현과 검증은 별도 승인 없이 진행한다. 방향이 바뀌는 결정만 사용자에게 묻고, 출시 준비가 끝나면 실제 배포 여부를 확인한다. 이 문서는 이후 작업의 기준이며 자동 실행 일정이나 상시 실행을 설정한 것은 아니다.

## 1 개발 범위와 기본 결정

|항목|기본 결정|
|---|---|
|프로젝트 범위|`주민센터/` 안에서 먼저 독립 개발하고 마지막에 본편과 연결|
|퍼즐|전입신고 전용 엔진 하나. 기존 비교·분류·기억·순서·경로 퍼즐의 판정 재사용 없음|
|핵심 재미|주민의 이사 사정을 이해하고 이동자·남는 사람·새 세대를 직접 구성|
|첫 지원|성인, 단일 이전 세대, 단일 전입지, 세대 구성 또는 기존 세대 편입|
|후속 검토|미성년자, 위임, 세대 합가, 전출지 세대주 이동, 별도 정정신고, 재등록·온라인 신고|

|챕터 분량|4일, 하루 3회 접수, 총 12회 접수. 11개의 서로 다른 사례와 1회 재방문|
|아트|따뜻한 종이색·초록색 단말기·픽셀 주민. 퍼즐 UI는 읽기 쉬운 일반 글꼴|
|런타임|현재 구조와 맞춘 순수 JavaScript·HTML·CSS. 서버·로그인·AI API 없이 실행|
|배포 산출물|외부 자원 없는 단일 HTML. 소스는 분리하고 빌드 시 합침|

모든 이름·주소·대화·사건은 창작한다. 화면에 실제 주민등록번호, 신분증 사진, 개인정보 업로드 기능을 만들지 않는다. 주민의 어려운 사정을 기만의 증거로 취급하지 않는다. 목표는 정당한 절차와 주민 안내를 함께 잘 수행하는 것이다.

## 2 현재 구현과 사용할 부분

현재 `src/core.js`에는 3사례, 불변 상태 변경 `initial/reduce`, 검토 `evaluate`, 검토 버전 확인 `canSubmit`이 있다. `src/app.js`는 전체 화면 렌더링, 이동·관계 입력·자료 dialog·완료 연출을 처리한다. `build.py`는 단일 HTML과 `preview/index.html`을 생성한다. 기존 검증은 순수 로직 20개와 Edge 브라우저에서 3사례 완료·오류 수정·undo·390px 화면 진행이다. 실제 휴대폰과 저장 복원은 아직 검증하지 않았다.

다음 부분은 새로 만든다.

|현재 시안의 상태|실제 개발에서 변경할 내용|
|---|---|
|모바일에서 전체 페이지가 길게 스크롤됨|작업 화면을 고정된 상단·중앙·하단 영역으로 재구성|
|접수 메모가 정답에 필요한 사실을 처음부터 모두 알려줌|관찰한 사실만 메모에 추가. 부족한 정보는 질문으로 확인|
|자료를 열면 읽음으로만 표시됨|자료 열람과 사례별 확인 상태를 분리|
|모든 문제의 주소 후보가 같음|사례별 주소 ID와 표시 문자열 사용|
|모든 선택 조작이 검토 revision을 변경함|업무 초안 revision과 화면 선택·열람 상태를 분리|
|되돌리기에 자료 열람도 들어감|업무 편집만 undo. 이미 확인한 주민 답변·자료는 유지|
|완료 뒤에도 입력을 바꿀 수 있음|완료 기록은 읽기 전용. 재도전은 새로운 무보상 연습 세션|
|완료 상태가 메모리에만 있음|결과·사건·기념품 지급을 저장 기록과 함께 한 번만 확정|
|본편과 분리된 시안|마지막 단계에서 확인된 최신 본편에 adapter로 연결|

로컬의 `game-core.js`는 5개 기존 퍼즐과 version 1 상태를 정의하고, `game-app.js`와 `scene-controller.js`는 `civil-servant-grow-v1` 저장 키를 사용한다. `build_game.py`는 기존 `공무원키우기_플레이.html`을 덮어쓴다. 이 정보를 배포본의 구조라고 가정하지 않으며, 주민센터 개발에는 기존 빌더를 사용하지 않는다. 본편 연결 시 최신 소스·빌드 입력·저장 구조를 별도로 확인한다.

## 3 플레이 구조와 성공 조건

한 접수는 주민 등장 → 요청 듣기 → 자료 열람과 질문 → 이동 대상 결정 → 이사 후 세대 구성 → 검토 → 전입 처리 또는 보완 안내 → 주민 반응 순서다. 한 문제의 목표 시간은 2~4분이며 첫 문제는 설명을 포함해 3~5분을 목표로 한다. 시간은 개발용 기록만 하고 점수·실패 조건으로 사용하지 않는다.

퍼즐의 판단은 다음 일곱 가지다.

1. 신고에서 실제로 이동하는 사람은 누구인가.
2. 이전 주소에 남는 사람과 세대주는 누구인가.
3. 새 주소와 상세주소가 충분히 확인되었는가.
4. 새 세대 구성인지 기존 세대 편입인지 확인되었는가.
5. 이사 후 세대주는 누구인가.
6. 이동자의 관계를 이사 후 세대주 기준으로 기록했는가.
7. 이 사례에서 필요한 확인이 갖춰졌는가, 부족하면 무엇을 안내해야 하는가.

최종 결과는 `registered`와 `followup_requested` 두 종류다. 전자는 유효한 기록과 확인이 갖춰졌을 때만 확정한다. 후자는 필요한 확인이 없고 적절한 보완 항목·사유를 안내했을 때 확정한다. 보완 안내를 성공으로 인정해도 세대 기록은 변경하지 않는다. 주민이 재방문하면 같은 사건의 별도 방문으로 다시 검토한다.

`자료 읽음`, `답변으로 확인`, `자료 갖춤`, `검토 통과`, `처리 확정`을 다른 상태로 표시한다. 자료창을 열었다는 이유만으로 본인 확인이나 신고 자격 확인이 완료되었다고 판정하지 않는다.

검토 오류는 3종류로 구분한다. 빈 필드에는 입력 위치를 안내하고, 이미 확인한 정보와 다른 초안에는 근거 자료 위치를 표시하며, 아직 알 수 없는 정보에는 질문 또는 보완 행동을 안내한다. 처음부터 숨겨진 정답을 오류 메시지로 공개하지 않는다. 힌트는 확인할 곳 → 판단 기준 → 이 사례의 설명 순서로 제공하며 모두 무료다.

## 4 모바일 UX 명세

우선 기준 화면은 390×844 CSS px, 최소 검증은 320×568이다. 360×640·412×915·430×932와 가로 화면에서도 기능을 유지한다. 600px 미만은 한 세대판, 600~899px은 공간에 따라 한 판 또는 두 판, 900px 이상은 두 판과 주민 자료 패널을 동시에 보여준다. 너비보다 실제 작업 공간 높이와 글자 확대 상태를 우선한다.

### 화면 영역

|영역|모바일 기본값|내용과 행동|
|---|---|---|
|상단 업무 표시|약 48px|접수번호·진행 단계·뒤로 가기|
|주민 요약|약 64~80px|얼굴·이름·핵심 요청 한 줄. 눌러 대화창 열기|
|자료와 질문 도구|약 44px|자료철·질문·확인된 사실 개수. 짧은 화면에서는 주민 요약에 통합|
|중앙 작업면|남은 공간|이사 전후 탭·세대판·주소·사람 카드·관계. 필요한 영역만 스크롤|
|하단 요약|약 28~40px|이동 2명·남음 1명 등 현재 변경 요약|
|하단 행동|약 64px와 safe area|주 행동 1개, 되돌리기 또는 수정 메뉴|

높이는 설계 시작값이며 절대 높이로 텍스트를 잘라내지 않는다. 기본은 `100dvh`, 미지원 환경은 `100vh`와 실제 화면 높이 보정으로 처리한다. 헤더·작업면·행동 영역을 grid 행으로 나누고 중앙에 `min-height:0; overflow:auto`를 적용한다. 화면 전체와 세대판이 동시에 스크롤되지 않게 한다. 320px·짧은 가로 화면·글자 200% 확대에서는 정보 접근을 우선해 문서형 스크롤로 전환한다.

### 네 단계의 화면과 행동

|단계|보여줄 내용|주 행동|전환 기준|
|---|---|---|---|
|접수|주민 요약·대화·신고 내용·확인 자료|세대 기록 작성|기초 요청을 읽으면 진행 가능. 미확인 항목은 그대로 남김|
|이동|이사 전 세대판·선택 표시·이사 후 탭의 인원|선택한 N명 옮기기|선택이 있어야 활성. 옮기면 이사 후 판으로 이동|
|구성|새 주소·세대 방식·카드별 세대주/관계|변경사항 확인|누르면 검토. 미완료여도 검토 위치를 안내|
|검토|이동자·남는 사람·새 주소·세대주/관계·확인 상태|전입 처리 또는 보완 안내|처리 조건이 맞을 때 해당 행동 활성|

이사 전후 탭에는 항상 인원과 이동 상태를 붙인다. 예를 들어 `이사 전 1명 남음 / 이사 후 2명 예정`으로 보여주고, 이사 후 화면에는 `김채림은 이전 집에 남음` 요약을 유지한다. 선택만 했을 때는 인원이 바뀌지 않으며 옮기기를 눌렀을 때 바뀐다.

사람 카드는 최소 높이 72px, 터치 영역은 최소 44px·주 행동은 48px 이상으로 시작한다. 본문 16px, 주요 설명 14px, 보조 표기 12px를 기본으로 한다. 이름·주소·관계는 말줄임으로 숨기지 않고 줄바꿈한다. 색과 체크 표시·텍스트를 함께 사용한다.

세대주 지정은 카드의 버튼으로 하고 관계는 카드 안 선택 버튼으로 연다. 관계 선택창 제목에 `이보람 → 세대주 이가온과의 관계`를 명시한다. 세대주 변경 시 변경 영향을 안내하고 필요한 관계만 미확인으로 되돌린다. 기존 세대 편입에서는 기존 세대주를 유지하며 임의 삭제·이동을 막는다. 본편 출시 범위에서는 기존 세대주 변경 사례를 넣지 않는다.

### 자료창과 예외 처리

자료와 질문은 아래에서 올라오는 한 개의 dialog로 연다. 닫기 버튼·Escape·뒤로 행동으로 닫을 수 있고, 포커스가 원래 버튼으로 돌아온다. dialog를 겹쳐 열지 않는다. 자료 내부만 스크롤하며 최대 높이는 이용 가능한 화면의 약 85%를 기준으로 한다. 확인·서명 등 현실 절차를 그대로 수행하는 UI가 아닌 사례별 게임 확인표임을 설명한다.

오류를 누르면 해당 세대판과 입력을 열고 강조한다. 수정 뒤에는 강조를 제거하고 기존 이동·주소·관계를 보존한다. 검토 화면으로 돌아갈 때 다시 평가한다. 물리적 뒤로 가기는 열린 자료창 닫기 → 이전 단계 → 접수 목록 순서로 동작한다. history에는 단계 변화만 넣고 사람 선택마다 새 항목을 만들지 않는다. file 실행과 브라우저별 동작은 실제 검증 후 지원 범위를 표시한다.

서식을 직접 타이핑하는 문제는 첫 출시에서 만들지 않는다. 따라서 모바일 키보드로 하단 버튼이 가려지는 상황을 기본 흐름에서 줄인다. 가로 회전·브라우저 주소창 높이 변화·자료창 종료·홈 화면 복귀 후에도 현재 단계와 초안을 유지한다.

## 5 최초 여섯 사례의 상세 계약

아래 주소는 콘텐츠 ID로 저장하고 화면에 문자열로 표시한다. 예시의 같은 이름·주소 후보를 무작위로 바꾸어 여섯 문제라고 세지 않는다. 각 사례는 새로운 판단을 하나씩 추가한다. 처음에는 사실을 충분히 제시하고, 뒤에서는 무료 질문을 통해 확인하도록 만든다.

|ID와 주민|이사 전과 요청|올바른 기록 또는 행동|새로 배우는 판단|
|---|---|---|---|
|M01 첫 번째 주소 · 윤새봄|새봄 한 사람. 들꽃길 3·101호에서 모퉁이로 12·201호로 이동|새봄만 이동, 새 세대, 새봄 세대주·본인. 필요한 확인 모두 갖춤|한 사람 선택·주소·세대주·검토·처리의 기본 조작|
|M02 함께 옮기는 집 · 서유진|유진·민재·해솔 모두 이동. 나무길 8·101호 → 모퉁이로 12·202호|3명 이동, 이전 집 남는 사람 없음, 새 세대주 유진. 민재 배우자·해솔 성인 자녀|전체 이동. 기존 시안 `all`을 이관|
|M03 첫 독립 · 이가온|어머니 채림은 기존 집에 남고 가온·보람만 이동|기존 세대주 채림 유지, 새 세대주 가온. 보람 형제자매|일부 이동과 관계의 기준. 기존 시안 `part`를 이관|
|M04 친구의 집으로 · 문다온|준서는 기존 집에 남고 다온만 최은오의 세대에 편입|다온만 이동, 기존 전입지 세대주 은오 유지, 다온 동거인|새 세대 구성과 기존 세대 편입의 차이. 기존 시안 `join` 이관|
|M05 마지막 한 자리 · 한여울|여울 한 사람 이동. 신고 내용에 건물만 있고 상세주소 확인이 필요|`정확한 호수를 다시 확인할까요?` 질문 후 302호 답변과 수정 내용 확보. 새 세대주 여울|불완전한 정보를 추측하지 않고 질문으로 해소|
|M06 오늘은 안내까지 · 배수아|수아가 강지후의 기존 세대로 편입할 요청. 필요한 사례 확인 항목 하나가 제시되지 않음|이동과 관계 초안은 작성 가능. 전입 확정은 불가. 누락 항목과 후속 안내를 선택해 `followup_requested`|올바른 보완 안내도 성공. 세대 기록 변경 없음|

M06의 누락 확인 항목은 구현 전에 현행 공식 서식과 해당 성인 사례 조건을 검토해 확정한다. 자료가 부족한 일반 게임 체크리스트를 실제 전국 공통 구비서류 규칙으로 표현하지 않는다. 이 항목은 사용자 취향 질문이 아니라 개발자가 원문으로 해결할 연구 작업이다. 확인 근거가 확보되지 않으면 해당 절차를 출제하지 않고 `신고 내용의 전입자 범위가 불명확해 확인이 필요한 상황`으로 바꿔 동일한 보완 판단을 구현한다. 변경 이유를 결정 기록에 남긴다.

M05는 답변 전에는 상세주소 ID가 확정되지 않는다. 후보를 우연히 맞혀도 확인 없이 처리를 통과할 수 없다. 답변을 받은 뒤에는 같은 질문이 같은 내용으로 유지되고 질문 횟수로 벌점을 주지 않는다. M06에서는 자료 누락이 고정된 사건 조건이며 오답 때문에 새로 생기는 문제가 아니다.

### 사례별 제작 산출물

각 사례는 초기 세대·공개 신고 내용·질문과 답변·자료 상태·허용 행동·검토 규칙·해설·힌트 3단계·정답 진행 기록·대표 오답 기록을 가진다. 정답 진행 기록은 검증용이며 일반 플레이 화면에 처음부터 공개하지 않는다. 모든 이동자와 남는 사람은 설명 또는 질문 답변으로 식별할 수 있어야 한다. 이야기 대사에 없는 정답을 데이터에만 넣지 않는다.

M01은 조작을 1단계씩 안내하고 모든 힌트를 켠다. M02~M04는 안내를 줄이되 업무 규칙을 자료창에서 상시 볼 수 있다. M05~M06는 질문과 자료 상태를 판단하게 한다. 실수 횟수와 플레이 시간은 결과 설명을 돕는 개발 기록이며 주민 신뢰나 보상을 깎는 수치로 쓰지 않는다.

## 6 퍼즐 엔진과 상태 계약

업무 사실, 플레이어 초안, 화면 표시, 검토 결과, 처리 기록을 분리한다. 콘텐츠는 JSON 데이터이며 임의 실행 함수나 스크립트를 저장하지 않는다.

```text
CaseDefinition → Session 생성 → Action 검증 → Draft 변경
                       ↓                         ↓
                  질문과 자료                규칙 검토
                       ↓                         ↓
                  확인된 사실         같은 revision으로 처리 확정
                                                 ↓
                                  저장된 결과와 사건 원장 → 화면 반영
```

|구조|주요 필드|계약|
|---|---|---|
|CaseDefinition|id, contentVersion, rulesVersion, people, beforeHousehold, destination, documents, questions, constraints, allowedOutcomes, witnesses|변경 불가 원형. 이동자·기존 전입지 인원 ID가 중복되지 않음|
|Draft|moverIds, addressId, householdMode, destinationHeadId, relationByPerson, disposition, followupReasonIds, revision|업무를 변경하는 행동만 revision 증가|
|Knowledge|seenDocumentIds, answeredQuestionIds, verifiedFactIds, evidenceStatusById|열람과 확인 구분. undo로 질문 답변을 잊지 않음|
|ViewState|phase, boardTab, selectionIds, openSheet, scrollByPanel, focusTarget|탭·선택·스크롤은 검토를 무효화하지 않음|
|Review|caseId, visitId, contentVersion, rulesVersion, draftRevision, knowledgeRevision, outcome, issues|확인 사실과 초안 버전이 모두 같아야 처리 가능|
|ResolvedRecord|resolutionId, caseId, visitId, outcome, beforeSnapshot, afterSnapshot, explanation, rewardClaims|완료 뒤 읽기 전용. 보완 결과 afterSnapshot은 beforeSnapshot과 같음|

초안과 사실은 각각 revision을 가진다. 질문 답변으로 사실이 바뀌면 검토를 무효화한다. 읽음 표시와 탭 이동만 바뀌면 유효 검토를 유지한다. undo와 redo는 업무 초안 최대 30개를 메모리에 두며 저장에는 현재 초안만 보관한다. 복원 후 undo 기록은 없지만 주민 설명과 작성 내용은 유지한다.

순수 엔진의 공개 API는 `createSession(caseDefinition)`, `dispatch(caseDefinition, session, action)`, `review(caseDefinition, session)`, `resolve(caseDefinition, session, review)`로 통일한다. `dispatch`는 허용되지 않은 ID·행동을 조용히 적용하지 않고 `accepted:false`와 사유를 반환한다. `resolve`는 새 상태와 결과를 반환하며 DOM·저장·보상을 직접 변경하지 않는다. 같은 resolutionId로 다시 호출하면 결과가 반복 지급되지 않는다.

검토는 초안 필드 존재, ID 유효성, 사람 이동의 보존, 주소 확인, 세대 구성, 세대주·관계, 필요한 사례 확인, 처리 결과 순서로 검사한다. UI에는 우선순위가 높은 오류 1개와 나머지 개수를 표시하고 전체 목록도 열 수 있게 한다. 상위 누락 때문에 의미가 없는 관계 오류를 여러 개 쌓지 않는다. 예를 들어 세대주가 없으면 관계 오류보다 세대주 지정을 먼저 안내한다.

### 상태 전환과 action의 영향

|action|업무 또는 사실 변경|검토와 화면에 미치는 영향|
|---|---|---|
|SELECT_PERSON / SWITCH_BOARD / OPEN_DOCUMENT|화면 선택·탭·읽음만 변경|검토 유지. 선택은 아직 이동 아님|
|MOVE_SELECTED / RETURN_PERSON|이동자 변경, 돌린 사람의 전입지 관계 삭제|업무 revision 증가, 검토 해제|
|SET_ADDRESS|전입지 주소 ID 변경|업무 revision 증가, 해당 주소에서만 유효한 기존 세대 편입 선택은 초기화|
|SET_HOUSEHOLD_MODE|새 세대 또는 편입 변경|업무 revision 증가, 세대주와 전입지 관계 재작성|
|SET_DESTINATION_HEAD|새 세대의 세대주 변경|업무 revision 증가, 이전 입력 관계를 미확인으로 되돌리고 새 세대주만 본인 지정|
|SET_RELATION|이동자의 전입지 세대주와 관계 변경|업무 revision 증가, 검토 해제|
|ASK_QUESTION / VERIFY_EVIDENCE|실제로 새 사실을 얻거나 사례 확인 상태 변경|knowledge revision 증가, 검토 해제. 같은 답변 재열람은 증가 없음|
|REQUEST_REVIEW|초안과 확인 사실을 평가|업무 데이터는 그대로. 검토 화면으로 이동|
|CONFIRM_REGISTRATION / CONFIRM_FOLLOWUP|유효한 검토를 기반으로 결과 확정|완료 상태로 이동. 업무 수정 action 거부|
|START_PRACTICE|완료 기록으로 새 연습 세션 생성|원래 기록·사건·기념품·보상은 유지|

단계는 `intake → moving → composing → review → resolved`이며 review 오류 수정은 해당 moving 또는 composing으로 돌아간다. 진행 단계와 별개로 자료창은 언제든 열린다. 구성 단계에서 보완 판단을 선택하면 검토가 followup_requested를 평가한다. 완료 뒤 뒤로 가기는 목록 또는 읽기 전용 기록으로만 이동한다.

전체 이동에서 이전 세대가 빈 경우 처리 후 snapshot은 `active:false, memberIds:[], headId:null`로 표현한다. 일부 이동에서는 이전 세대의 세대주와 남은 구성원의 관계를 유지한다. beforeSnapshot과 afterSnapshot은 이전 세대와 전입지 세대를 모두 포함하며, 새 주소의 기록만 저장해 이전 세대 변경을 빠뜨리지 않는다.

예를 들어 M03의 초기 이전 세대 관계는 `채림:본인, 가온:자녀, 보람:자녀`이고, 처리 후 새 세대 관계는 `가온:본인, 보람:형제자매`다. 원래 집은 채림만 남고 새집은 가온·보람 두 명이 된다. 같은 사람이 세대주 기준 변화로 다른 관계 값을 갖는 것을 엔진과 설명에서 함께 검증한다.

### 반드시 지켜야 할 불변 조건

- 사람은 이사 전후에서 중복되거나 사라지지 않는다. 기존 전입지 사람은 이동 대상이 아니다.
- 단일 세대에는 세대주가 한 명만 존재한다. 세대주의 관계는 본인으로만 기록한다.
- 이동하지 않은 원래 세대의 관계·세대주를 새 전입지 변경으로 덮어쓰지 않는다.
- 기존 세대 편입의 기존 세대주는 첫 출시에서 변경할 수 없다.
- 실제 처리 전에는 원형 세대가 변경되지 않는다. 보완 안내는 세대를 변경하지 않는다.
- 알 수 없는 관계를 이름·성별·나이·가족 호칭만으로 자동 추측하지 않는다.
- 편집 또는 새로운 확인 사실 뒤에는 이전 검토를 처리 확정에 사용할 수 없다.
- 완료 기록의 수정은 불가하다. 다시하기는 새로운 연습 세션으로 열며 보상은 없다.

## 7 파일 구조와 구현 방식

기존 `src`를 점진적으로 분리하고 매 단계에서 실행 가능한 빌드를 유지한다. 새 구조가 완성되기 전 시안 파일을 삭제하지 않는다.

```text
주민센터/
  개발계획.md
  README.md
  docs/
    개발작업목록.json
    개발진행.md
    결정기록.md
    절차근거.json
  src/
    shell.html, style.css, app.js
    data/cases.js, dialogue.js, chapter.js, items.js
    engine/session.js, actions.js, review.js, resolve.js
    ui/workspace.js, sheets.js, cards.js, review-screen.js
    services/storage.js, migration.js, campaign.js
    adapters/main-game.js
  assets/
    portraits/, props/, map/
  tests/
    engine/, content/, storage/, browser/
  build.py
  전입신고_퍼즐시안.html
  전입신고_퍼즐.html
  preview/index.html
```

이 구조는 계획이다. 현재 존재하는 파일 목록은 README와 개발진행 문서에서 따로 기록한다. `cases.js`는 데이터 원형을 제공하며 Node 테스트와 브라우저 양쪽에서 읽을 수 있게 한다. 빌더가 데이터·엔진·UI를 정해진 의존 순서로 단일 파일에 포함하고 외부 import·fetch 없이 실행한다. 콘텐츠 문자열은 텍스트 노드 또는 escape를 거쳐 표시한다. 인라인 script 종료 문자열은 빌드에서 검사하고 JSON 삽입 시 안전하게 escape한다.

스타일은 간격·폰트·색·터치 크기를 CSS 변수로 정리한다. 루트에 주민센터 namespace를 적용해 본편 스타일과 충돌을 줄인다. 주민 픽셀 그림은 현재 자체 SVG를 먼저 사용하고 실제 인물 그림은 UI 통과 뒤 제작한다. 화면 이벤트는 명시적 action으로 엔진에 전달하고 렌더 함수 안에서 처리·보상·저장을 수행하지 않는다.

전체 DOM을 매 조작마다 교체하는 현재 구조는 정적 껍데기와 개별 영역 갱신으로 바꾼다. 주민 요약, 선택 카드, 이사 후 구성, 검토 상태를 독립 갱신하며 포커스·중앙 스크롤·자료창 상태를 보존한다. 성능이 충분한지 확인한 뒤 불필요한 프레임워크 도입이나 전면 재작성은 하지 않는다.

## 8 저장과 처리 확정

독립 퍼즐 저장 키는 `gong-game:resident-center:v1`로 한다. 기존 `civil-servant-grow-v1`을 읽거나 쓰지 않는다. 저장 envelope에는 schemaVersion, contentVersion, savedAt, campaign, activeSession, records, eventLedger, itemClaims, settings를 둔다. 디스크에 기록할 값은 JSON으로 복원 가능한 데이터만 사용한다.

업무 변경과 질문 답변 뒤에는 최대 300ms 단위로 저장을 묶고, 처리 확정·사례 나가기·페이지 숨김 전에는 즉시 저장한다. pagehide 때만 저장하는 방식에 의존하지 않는다. 실행 종료 직전에 저장이 보장된다고 주장하지 않으며 마지막 성공 저장 시점을 복원 기준으로 한다.

처리 확정은 최신 검토 확인 → 순수 resolve → 다음 전체 저장본 작성 → 단일 envelope 저장 → 화면 완료 표시 순서다. 처리 기록과 한 번만 발생할 사건·소품 지급 ID를 같은 envelope에 기록한다. 저장 성공 뒤 화면이 닫혀도 복원 시 완료 상태가 된다. double tap·다시 열기·재방문으로 같은 visitId의 결과를 두 번 만들지 않는다.

저장 불가일 때는 메모리로 계속 플레이하게 하고 `이 환경에서는 종료 후 복원이 보장되지 않습니다`를 표시한다. 결과를 잃지 않도록 JSON 내보내기를 제공한다. 가져오기는 파일 크기·schema·ID·배열 길이·값 타입을 검증하고 별도 복사본에서 적용한다. 잘못된 파일이 현재 기록을 초기화하지 않는다.

contentVersion이 바뀌면 미완료 초안을 현행 사례와 대조한다. 호환되지 않으면 기존 초안을 백업하고 해당 접수만 새로 시작한다. 완료 기록과 소유 기념품은 보존한다. 미래 schema는 무리하게 해석하거나 덮어쓰지 않고 원본 내보내기와 새 독립 세션을 제공한다. storage 이벤트로 다른 탭의 변경을 감지하면 오래된 화면에서 처리를 막고 최신 상태를 다시 불러온다. 첫 출시는 한 탭 플레이를 지원하며 두 탭의 동시 진행 병합은 하지 않는다.

file://의 저장 지원은 브라우저별로 다를 수 있으므로 실패 모드와 내보내기를 함께 시험한다. GitHub Pages와 로컬 file 실행은 서로 다른 저장 공간으로 취급하고 자동 공유를 약속하지 않는다.

## 9 실제 자료를 콘텐츠에 반영하는 기준

2026년 10월 11일에 확인한 [미추홀구 전입신고 안내](https://www.michuhol.go.kr/main/content.do?sq=69)는 전체 이동과 일부 이동·편입 등에 따른 서식을 안내한다. [주민등록법 시행령 별지 제15호의2서식](https://law.go.kr/LSW/flDownload.do?bylClsCd=110202&flSeq=163702297&gubun=)은 전입 전후 세대, 상세주소, 전입지 세대주와의 관계 및 사례별 확인 항목을 포함한다. 이 사실을 세대 구성 퍼즐의 기준으로 사용한다. 원문 안내와 서식의 범위를 넘어 모든 신고 유형의 요건이 동일하다고 일반화하지 않는다.

`절차근거.json`에는 sourceId, 제목, URL, 확인일, 원문 위치, 확인한 사실, 적용 사례, 게임에서 단순화한 부분, 추가 확인 필요 여부를 기록한다. 현행 서식을 우선하고 오래된 기관 안내와 차이가 있으면 해당 항목을 출제하기 전에 다시 확인한다. 기한·수수료·계약서·세대주 변경·미성년자 절차를 첫 여섯 문제의 정답 조건에 추가하지 않는다.

실제 공문·공개 민원 답변·정보공개 자료는 주민센터의 설명 방식, 반복 방문의 원인, 인계와 기록 관리의 맥락을 만들 때 조사한다. 비공개 민원 원문이나 실제 인물의 사연을 수집하는 방식으로 진행하지 않는다. 개별 민원의 지역·사실을 허구 사건과 혼합해 실제 있었던 사건처럼 설명하지 않는다. 자료가 없으면 창작 사건임을 명시하고 확인된 절차만 반영한다.

## 10 퍼즐 다음에 붙일 이야기와 맵

주민센터의 이야기 주제는 `주소를 옮기는 사람들의 새로운 시작을 제대로 안내하는 첫 근무`다. 발령 사유는 업무 순환이며 이전 부서의 실패나 징계로 설정하지 않는다. 첫 출근의 선임은 답을 대신 입력하지 않고 주민의 요청과 기록이 다른 지점을 확인하도록 도와준다.

|근무일|접수 순서|이야기의 기능|
|---|---|---|
|1일|M01 → M02 → M03|새 창구의 기본 조작, 온 가족 이사, 첫 독립|
|2일|M04 → M05 → M06 첫 방문|다른 세대로 들어가기, 질문하기, 확인이 부족하면 안내하기|
|3일|M06 재방문 → M07 → M08|어제 안내가 오늘 처리로 이어짐. 주민의 상황을 기억하는 창구|
|4일|M09 → M10 → M11|배운 판단의 조합, 생활보장과 인물의 안부, 근무 결산|

12는 방문 수이고 독립 사례 수는 11이다. M06 첫 방문은 올바른 보완 안내로 해당 근무 슬롯을 마치지만 사건은 대기 상태로 남는다. 재방문은 새로운 visitId로 기록하며 같은 세대의 변경은 마지막 전입 처리에서만 발생한다. 재방문에 필요한 게임 확인은 3일 시작에 제공하고 실제 시간 대기를 요구하지 않는다.

M07~M11은 엔진 확정 후 작성한다. 단순 이름 변경이 아니라 이동자 범위·관계 기준·정보 확인을 두 가지씩 조합한 성인 사례로 만들고, 첫 출시 범위를 벗어난 절차는 추가하지 않는다. 4일의 근무 목표는 각 8~12분, 전체 목표는 35~50분이다. 이 시간은 실제 첫 플레이 기록으로 조정한다.

등장인물은 선임 1명, 창구 동료 1명, 기존 생활보장과 인물 1명부터 만든다. 기존 인물의 이름·성격·관계 플래그는 본편 데이터 확인 후 사용한다. 연결이 확인되기 전에는 새 이름으로 기존 인물을 대체하지 않는다. 복지 관련 이야기는 안내·다른 담당자와의 연결 대사로 처리하고 신규 복지 퍼즐로 확장하지 않는다.

주민센터 맵은 20×14 논리 격자 한 장으로 시작한다. 입구·번호표와 대기석·전입 창구·서식대·자료함·직원 책상 여섯 구역을 둔다. 모바일에서는 걸어 다니기를 필수로 만들지 않고 목적지를 누르면 이동한다. 전입 창구를 누르면 전체 작업 화면으로 전환하며 뒤로 가면 같은 맵 위치로 돌아온다. 입구에서 모든 필수 목적지까지 이동 경로가 있어야 하고 플레이 중 통로를 소품이 막지 않게 한다.

첫 비품은 번호표 기계, 서식 받침, 주소 안내판, 처리 자료함, 세대 기록철, 선임의 책상이다. 기념품은 첫 업무 이름표·접수 메모장·동네 지도 엽서·창구 사진 4개로 시작한다. 이름표는 첫 처리, 메모장은 2일 결산, 엽서는 M06 재방문 완료, 사진은 4일 결산에 한 번 지급한다. 주소 안내판은 무료 업무 도구이며 정답을 자동 입력하지 않는다. 첫 챕터에는 별도 유료 상점을 만들지 않는다.

MC00에서는 기존 퍼즐 시안과 테스트를 재실행해 보호 기준을 기록한다. 원본 HTML을 생성하는 기존 빌더를 실행하지 않는다. MC01에서는 하드코딩된 3사례를 데이터 파일로 옮기고 M01·M05·M06 데이터 계약을 추가한다. MC02에서는 업무 초안과 선택·질문 상태를 분리하고 의미 있는 업무 행동만 undo에 넣는다. MC03에서는 보완 안내와 최종 확정을 추가하고 완료 뒤 재편집을 차단한다. 이후 MC04에서 실제 모바일 화면을 만든다.

UI 조작의 목표는 일반적인 선택·탭·관계 설정이 100ms 안에 화면에 반영되고 저사양 기기에서 긴 멈춤 없이 실행되는 것이다. 초기 자체 포함 HTML은 1.5MB 이하를 목표로 하며 이미지는 필요할 때만 추가한다. 목표를 넘으면 실제 측정 원인과 조정 내용을 기록한다. 모바일 에뮬레이션은 실제 기기 검증으로 표기하지 않는다. 실제 Android·iOS 기기를 사용할 수 없으면 출시 후보에 미검증 항목을 남기고 지원 확인을 보류하되 나머지 개발은 계속한다.

사용성 목표는 첫 문제에서 이동자 선택·옮기기·검토가 외부 설명 없이 가능하고, 이후 문제에서 사용자가 업무 정보 확인에 집중하는 것이다. 첫 시도에 오류가 생겨도 위치 안내로 스스로 수정할 수 있어야 한다. 가능한 경우 처음 보는 플레이어 3명 정도의 짧은 관찰을 활용하되 사람 모집이나 연락은 자동으로 하지 않는다. 관찰이 없으면 자동 시험 통과를 사용성 검증 완료로 바꾸어 보고하지 않는다.

## 13 개발 운영과 자율 결정

작업 시작 시 개발진행 문서와 작업 목록을 읽고 선행 조건을 만족한 가장 앞의 작업을 진행한다. 계획 항목에 `planned`, 실제 작업에 `in_progress`, 통과 증거가 있는 완료에 `done`을 사용한다. 테스트 수나 화면 완성만으로 단계 전체를 완료 처리하지 않는다. 완료한 작업의 산출물·검증·남은 문제와 다음 작업 ID를 `docs/개발진행.md`에 갱신한다.

routine 변경은 개발자가 결정한다. 간격·문구·색상·내부 파일 분리·예외 처리·힌트·가상 이름·문제 순서의 작은 조정은 질문 없이 진행한다. 변경 이유와 영향을 `docs/결정기록.md`에 남긴다. 법적 사실은 원문 확인으로 해결하고 미확인 조건은 출제에서 빼거나 범위를 좁힌다.

사용자에게 확인할 항목은 전입신고 외 다른 퍼즐 추가, 유료 기능·계정·외부 API 도입, 기존 진행 초기화, 첫 출시 범위의 큰 변경, 공개 배포 등이다. 확인이 필요하더라도 관련 없는 구현을 멈추지 않는다. 배포 승인은 검토 가능한 최종 빌드와 변경 목록을 만든 뒤에 요청한다. 공개 GitHub 반영이나 외부 메시지 전송을 이 계획만으로 수행하지 않는다.

진행 보고는 완료된 기능·검증 결과·다음 단계·중요한 범위 변경만 간단히 전달한다. 단계마다 시안을 보낼 수 있지만 사용자가 답해야 다음 단계로 갈 수 있는 승인 절차를 만들지 않는다. 대화가 이어지면 이 기준으로 개발을 재개하며 별도 자동화가 설정되지 않은 상태에서 대화 밖 작업을 계속한다고 약속하지 않는다.

## 14 최종 인수 조건

독립 퍼즐의 완료는 여섯 사례 모두 처리 또는 보완 안내가 가능하고, 모바일 전용 작업면·무료 질문·관계 기록·최종 검토·수정·저장 복원·완료 잠금·연습 무보상·결과 기록이 함께 동작할 때다. 이 단계에서는 맵과 기존 게임 연결이 없어도 독립 퍼즐 완성을 선언할 수 있다.

주민센터 챕터의 완료는 인사발령 → 4일 12접수 → M06 재방문 처리 → 동료와 기존 인물 연결 → 맵 복귀 → 기념품 → 근무 결산까지 이어지고 본편 저장 보존과 회귀가 통과했을 때다. 교통행정과는 다음 발령의 예고만 두고 아직 구현되지 않은 챕터 진입 버튼은 활성화하지 않는다.

다음 실제 착수 작업은 MC00이다. MC00 이후 MC01~MC11까지를 우선 완료하고, 독립 퍼즐이 안정된 뒤 MC12 이후를 진행한다.
